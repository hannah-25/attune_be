# 실행 계획: 실사용 환경 검증

- 상태: active
- 작성자 / 날짜: Codex / 2026-07-29
- 선행 결과: [dev 100 VU 부하 테스트](2026-07-28-dev-load-test.md)

## 목표

dev 환경에서 실제 외부 연동, 실제 클라이언트 E2E, 장기 안정성, 운영 준비 절차를 순차 검증한다. 이 계획의 완료는 **출시 전 검증 근거**를 만드는 것이며, 운영 환경에서의 완전한 동등성을 주장하지는 않는다.

## 현재 상태

- 인증·조회·복약 기록 중심의 100 VU 단기 부하 테스트는 통과했다. 100 VU에서 오류율 0%, p95 87.01 ms였고 CPU는 약 94%였다.
- 개발 서버는 일반 `dev` 프로파일로 복구됐고 전용 부하 테스트 데이터는 삭제됐다.
- 자동화 통합 테스트는 Gemini, Google Calendar, OAuth, JavaMailSender를 mock/stub으로 격리한다. 실제 공급자와의 연결은 아직 별도로 검증하지 않았다.

## 범위와 제외 범위

### 포함

1. 실제 외부 연동: Google·Kakao·Apple OAuth, Google Calendar, Gemini, Gmail SMTP, Web Push
2. 실제 dev 웹/앱 클라이언트에서의 핵심 사용자 E2E 흐름
3. 외부 호출을 제외한 100 VU 장기 안정성 시험
4. 배포·관측·롤백·데이터 정리 확인

### 제외

- 운영 사용자, 운영 DB, 운영 발송 대상에 대한 시험
- 마케팅 메일/푸시 대량 발송과 실제 사용자 콘텐츠 사용
- 외부 공급자 장애를 인위적으로 대량 유발하거나 할당량을 소진하는 시험
- 모바일 OS별 실기기 전체 호환성 인증. 실제 앱이 준비되면 별도 기기 매트릭스로 확장한다.

## 사전 승인 게이트

아래 조건이 충족되기 전에는 실제 외부 호출을 실행하지 않는다.

| 항목 | 필요한 준비 | 안전 기준 |
| --- | --- | --- |
| OAuth | 공급자별 테스트 계정과 dev redirect URI 등록 | 개인 계정 1개씩만 사용, 토큰·인증 코드는 기록하지 않음 |
| Google Calendar | 전용 테스트 Google 계정·빈 캘린더 | 읽기 전용 확인부터 시작, 테스트 일정만 사용 |
| Gemini | dev API 키와 호출 예산 | 합성·비식별 입력, 기능당 최소 성공 1회와 오류 경로 1회만 실행 |
| Gmail SMTP | 수신 가능한 전용 테스트 메일함 | 회원가입/재설정 등 필요한 메일만 발송, 대량 발송 금지 |
| Web Push | dev HTTPS 클라이언트와 전용 브라우저 프로필 | 전용 구독 1개, 테스트 메시지 1건씩, 수신 영수증 확인 |

**실행 승인 필요:** 테스트 계정·수신 주소·Gemini 예산이 준비되었는지 확인하고, 실제 발송 및 실제 Gemini 호출을 허용한다는 사용자 승인을 받은 뒤 1단계를 시작한다.

## 작업 단계

### 1. 실제 외부 연동 검증 — 우선 실행

각 항목은 정상 경로, 안전한 실패 경로, 서버 관측 지표를 함께 확인한다.

| 연동 | 정상 경로 | 실패 경로 | 통과 기준 |
| --- | --- | --- | --- |
| Google/Kakao/Apple OAuth | 공급자 로그인 후 Attune 계정 생성·재로그인 | 유효하지 않거나 만료된 토큰 | 계정 중복 생성 없음, 안전한 4xx/5xx 응답, JWT 발급·로그아웃 확인 |
| Google Calendar | OAuth code 연결, 계정/캘린더/테스트 일정 동기화 | 연결 해제 또는 만료 토큰 | 일정 조회 결과 일치, 재연동 안내, 토큰·이메일 비노출 |
| Gemini | 온보딩 추천 및 복약 분석 리포트 각 1회 | 공급자 오류를 mock으로 재현하는 기존 테스트 확인 | 응답 파싱·저장 성공, 사용자 친화 오류, 요청/지연 metric 기록 |
| Gmail SMTP | 가입 인증 또는 비밀번호 재설정 메일 1건 수신 | 잘못된 수신 주소는 테스트 환경에서만 확인 | 실제 메일 수신, 비밀번호/토큰 로그 미노출, 실패 metric 기록 |
| Web Push | 구독 등록 → 단일 테스트 알림 → 수신/열람 영수증 | 구독 해제 뒤 발송 또는 만료 구독 | 기기에 표시되고 알림함·receipt 일치, invalid subscription이 안전하게 처리 |

각 완료 뒤 전용 계정의 연동 토큰·구독·테스트 일정·테스트 데이터를 삭제한다. 공급자 실패 경로 중 실제로 안전하게 만들 수 없는 것은 기존 단위/통합 테스트로 검증하고, 실제 공급자에 장애를 유발하지 않는다.

### 2. 실제 클라이언트 E2E

dev 웹/앱에서 다음 흐름을 한 사용자 기준으로 처음부터 끝까지 수행한다.

1. 이메일 가입 또는 각 소셜 로그인 → 약관 동의 → 온보딩 AI 추천 확인·수정·저장
2. 복약 등록 → 스케줄 생성 → 오늘 복약 기록 → 복용 통계·AI 리포트 확인
3. 일지/태그/목표 기록 → 일정·할 일 작성 → Google Calendar 동기화 확인
4. 알림 구독 → 테스트 알림 수신/열람 → 알림함 상태 확인
5. 비밀번호 재설정, 로그아웃/재로그인, 토큰 만료 후 재인증
6. 계정 삭제 후 로그인·외부 연동·개인 데이터 접근 불가 확인

각 단계에서 화면 표시, API 응답, DB에 저장된 결과가 일치하는지 확인한다. 실패 시 응답의 `requestId`로 서버 로그와 외부 연동 metric을 추적한다.

### 3. 장기 안정성 시험

- 대상: `api-dev.attune-me.com`, `dev,loadtest` 프로파일, 전용 100개 계정
- 시나리오: 기존 k6의 80% 조회·20% 복약 기록. 실제 Gemini·메일·푸시·OAuth·Calendar 호출은 포함하지 않는다.
- 부하: 25 VU 30분 워밍업 → 100 VU 4시간 유지 → 15분 0 VU 종료 관찰
- 수집: k6 오류율·p95/p99·RPS, readiness, Hikari active/pending, JVM heap/GC, 컨테이너 CPU/메모리, 오류 로그
- 중단 기준: 5xx 또는 요청 실패율 1% 이상, readiness 실패, Hikari pending 지속 발생, CPU 95% 이상이 10분 지속, 힙이 지속 증가하거나 OOM 징후 발생
- 종료 후: 전용 데이터 cleanup, `loadtest=false`로 dev 일반 프로파일 복구

### 4. 운영 준비 확인

1. dev 배포 후 readiness 통과와 정상 API 확인
2. 배포 전 CI, secret 존재 여부, migration 여부를 체크리스트로 확인
3. 롤백 절차를 dev에서 문서대로 1회 리허설하되, 운영에는 적용하지 않음
4. 오류가 발생한 시험에서는 `requestId` → 애플리케이션 로그 → Actuator → metric 순서로 원인 추적 가능함을 확인
5. 모든 테스트 계정·외부 연결·수신 구독·테스트 일정과 산출물에 토큰/개인정보가 남지 않았는지 확인

## 검증 산출물

- 기능별 실행 일시, 테스트 계정 식별자(비밀 제외), 정상/실패 결과, requestId, 관련 metric 요약
- E2E 체크리스트의 단계별 통과/실패 및 증빙 스크린샷 또는 비밀 없는 응답 요약
- 장기 시험 k6 요약: VU, 기간, 요청 수, RPS, p50/p95/p99, 오류율, 자원 최고치
- 발견 이슈: 재현 절차, 영향도, 임시 조치, 수정 PR 링크

## 완료 조건

- [ ] 외부 연동 5종의 정상 경로와 안전한 실패 경로를 기록했다.
- [ ] 실제 클라이언트 핵심 E2E 흐름과 계정 삭제를 통과했다.
- [ ] 100 VU 4시간 장기 안정성 기준을 통과하거나, 실패 원인과 개선 조치를 확정했다.
- [ ] 배포·관측·롤백·정리 절차를 dev에서 검증했다.
- [ ] 모든 전용 데이터·외부 연결·테스트 구독을 삭제했고 dev를 일반 프로파일로 복구했다.

## 위험과 롤백

- 실제 메일·푸시·Gemini 호출은 비용과 외부 영향을 일으킬 수 있으므로 사전 승인 없이 실행하지 않는다.
- OAuth/Calendar 권한은 테스트 계정에만 부여하고, 완료 후 공급자 콘솔과 앱에서 모두 연결을 해제한다.
- 외부 연동 또는 부하 시험 중 문제 발생 시 테스트를 중지하고 `loadtest=false`로 dev를 복구한다. 애플리케이션 코드 변경이 필요하면 별도 feature 브랜치와 PR로 수정한다.
