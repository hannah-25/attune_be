# 실행 계획: 실사용 환경 검증

- 상태: active
- 작성자 / 날짜: Codex / 2026-07-29
- 선행 결과: [dev 100 VU 부하 테스트](2026-07-28-dev-load-test.md)

## 목표

dev 환경에서 실제 외부 연동, 실제 클라이언트 E2E, 장기 안정성, 운영 준비 절차를 순차 검증한다. 이 계획의 완료는 **출시 전 검증 근거**를 만드는 것이며, 운영 환경에서의 완전한 동등성을 주장하지는 않는다.

## 현재 상태

- 인증·조회·복약 기록 중심의 100 VU 단기 부하 테스트는 통과했다. 100 VU에서 오류율 0%, p95 87.01 ms였고 CPU는 약 94%였다.
- 개발 서버는 일반 `dev` 프로파일로 복구됐고 전용 부하 테스트 데이터는 삭제됐다.
- 자동화 통합 테스트는 Gemini, Google Calendar, OAuth, JavaMailSender를 mock/stub으로 격리한다. 실제 공급자와의 연결은 아직 별도로 검증하지 않았다.

## 범위와 제외 범위

### 포함

1. 실제 외부 연동: Google·Kakao·Apple OAuth, Google Calendar, Gemini, Gmail SMTP, Web Push
2. 실제 dev 웹/앱 클라이언트에서의 핵심 사용자 E2E 흐름
3. 외부 호출을 제외한 100 VU 장기 안정성 시험
4. 배포·관측·롤백·데이터 정리 확인
5. 관리자 메일·공지 푸시·마케팅 푸시를 전용 테스트 계정 묶음에 실제 발송

### 제외

- 운영 환경 자체에 대한 시험. 현재 운영 서버가 없으므로 dev가 실제 사용 환경 대체 대상이다.
- 외부 공급자 장애를 인위적으로 대량 유발하거나 Gemini·OAuth·Google API 할당량을 소진하는 시험
- 모바일 OS별 실기기 전체 호환성 인증. 실제 앱이 준비되면 별도 기기 매트릭스로 확장한다.

현재 실제 사용자가 없으므로 dev에 존재하는 데이터는 모두 테스트 대상으로 취급할 수 있다. 다만 재현성·정리 검증을 위해 새 데이터는 `e2e-*` 접두사의 전용 계정으로 만들고, 완료 뒤 삭제한다.

## 사전 승인 게이트

아래 조건이 충족되기 전에는 실제 외부 호출을 실행하지 않는다.

| 항목 | 필요한 준비 | 안전 기준 |
| --- | --- | --- |
| OAuth | 공급자별 테스트 계정과 dev redirect URI 등록 | 개인 계정 1개씩만 사용, 토큰·인증 코드는 기록하지 않음 |
| Google Calendar | 전용 테스트 Google 계정·빈 캘린더 | 읽기 전용 확인부터 시작, 테스트 일정만 사용 |
| Gemini | dev API 키와 총 1,000원 호출 예산 | 합성·비식별 입력, 기능당 최소 성공 1회와 오류 경로 1회만 실행 |
| Gmail SMTP | 수신 가능한 전용 테스트 메일함 10개 이하 | 가입·재설정·약관 변경·관리자 발송 경로를 실제 수신으로 확인 |
| Web Push | dev HTTPS 클라이언트와 전용 브라우저 프로필 | 전용 구독 10개 이하, 일반·공지·마케팅 발송과 수신 영수증 확인 |

**실행 승인 필요:** 테스트 계정·수신 주소가 준비되었는지 확인하고, 실제 발송 및 총 1,000원 한도의 Gemini 호출을 허용한다는 사용자 승인을 받은 뒤 1단계를 시작한다.

### 테스트 대상 준비 방법

1. **Google 계정 1개** — Chrome의 별도 프로필에서 로그인하고, Google Calendar에 `Attune E2E`라는 빈 캘린더와 테스트 일정 1~2개를 만든다. 이 계정은 Google 로그인과 Calendar 연결에 함께 사용한다.
2. **Kakao 계정 1개, Apple ID 1개** — 각각 별도 브라우저 프로필 또는 시크릿 창에서 로그인한다. 공급자 콘솔에서 dev 프론트엔드 origin/redirect URI가 등록돼 있어야 한다. Apple은 Sign in with Apple이 켜진 개발자 앱과 해당 redirect URI가 필요하다.
3. **테스트 메일함 1개** — Gmail이라면 `계정명+e2e01@gmail.com`처럼 `+` 별칭을 최대 10개 사용해도 모두 같은 받은편지함에서 확인할 수 있다. 발송 검증용 계정은 이 별칭으로 만든다.
4. **Web Push 브라우저 1개** — 위 Chrome의 별도 프로필에서 `dev.attune-me.com`에 접속해 알림 권한을 허용하고, 전용 `e2e-*` 계정으로 로그인해 구독을 등록한다. 테스트 중에는 해당 브라우저를 열어 둔다.
5. **Gemini** — dev 키가 이미 배포 시 주입되는지만 확인한다. 실제 호출은 온보딩 1회와 복약 분석 1회부터 시작하고, 누적 예상 비용이 1,000원에 닿으면 즉시 중지한다.

비밀번호, OAuth access token, 인증 코드, Gemini 키는 채팅·문서·테스트 결과에 기록하거나 공유하지 않는다.

## 작업 단계

### 1. 실제 외부 연동 검증 — 우선 실행

각 항목은 정상 경로, 안전한 실패 경로, 서버 관측 지표를 함께 확인한다.

| 연동 | 정상 경로 | 실패 경로 | 통과 기준 |
| --- | --- | --- | --- |
| Google/Kakao/Apple OAuth | 공급자 로그인 후 Attune 계정 생성·재로그인 | 유효하지 않거나 만료된 토큰 | 계정 중복 생성 없음, 안전한 4xx/5xx 응답, JWT 발급·로그아웃 확인 |
| Google Calendar | OAuth code 연결, 계정/캘린더/테스트 일정 동기화 | 연결 해제 또는 만료 토큰 | 일정 조회 결과 일치, 재연동 안내, 토큰·이메일 비노출 |
| Gemini | 온보딩 추천 및 복약 분석 리포트 각 1회 | 공급자 오류를 mock으로 재현하는 기존 테스트 확인 | 응답 파싱·저장 성공, 사용자 친화 오류, 요청/지연 metric 기록 |
| Gmail SMTP | 가입 인증·비밀번호 재설정·약관 변경·관리자 발송을 전용 10계정에 수신 | 잘못된 수신 주소는 테스트 환경에서만 확인 | 각 유형이 실제 수신되고, 비밀번호/토큰 로그 미노출, 성공·실패 metric 기록 |
| Web Push | 구독 등록 → 일반·공지·마케팅 테스트 발송 → 수신/열람 영수증 | 구독 해제 뒤 발송 또는 만료 구독 | 각 발송 유형이 기기에 표시되고 알림함·receipt 일치, invalid subscription이 안전하게 처리 |

각 완료 뒤 전용 계정의 연동 토큰·구독·테스트 일정·테스트 데이터를 삭제한다. 공급자 실패 경로 중 실제로 안전하게 만들 수 없는 것은 기존 단위/통합 테스트로 검증하고, 실제 공급자에 장애를 유발하지 않는다.

### 2. 실제 클라이언트 E2E

dev 웹/앱에서 다음 흐름을 한 사용자 기준으로 처음부터 끝까지 수행한다.

1. 이메일 가입 또는 각 소셜 로그인 → 약관 동의 → 온보딩 AI 추천 확인·수정·저장
2. 복약 등록 → 스케줄 생성 → 오늘 복약 기록 → 복용 통계·AI 리포트 확인
3. 일지/태그/목표 기록 → 일정·할 일 작성 → Google Calendar 동기화 확인
4. 알림 구독 → 테스트 알림 수신/열람 → 알림함 상태 확인
5. 비밀번호 재설정, 로그아웃/재로그인, 토큰 만료 후 재인증
6. 계정 삭제 후 로그인·외부 연동·개인 데이터 접근 불가 확인

각 단계에서 화면 표시, API 응답, DB에 저장된 결과가 일치하는지 확인한다. 실패 시 응답의 `requestId`로 서버 로그와 외부 연동 metric을 추적한다.

### 3. 장기 안정성 시험

- 대상: `api-dev.attune-me.com`, `dev,loadtest` 프로파일, 전용 100개 계정
- 시나리오: 기존 k6의 80% 조회·20% 복약 기록. 실제 Gemini·메일·푸시·OAuth·Calendar 호출은 포함하지 않는다.
- 부하: 25 VU 30분 워밍업 → 100 VU 4시간 유지 → 15분 0 VU 종료 관찰
- 수집: k6 오류율·p95/p99·RPS, readiness, Hikari active/pending, JVM heap/GC, 컨테이너 CPU/메모리, 오류 로그
- 중단 기준: 5xx 또는 요청 실패율 1% 이상, readiness 실패, Hikari pending 지속 발생, CPU 95% 이상이 10분 지속, 힙이 지속 증가하거나 OOM 징후 발생
- 종료 후: 전용 데이터 cleanup, `loadtest=false`로 dev 일반 프로파일 복구

- 상태: **완료**

- 사전 배포: 전용 계정 생성은 [deploy run #30479898571](https://github.com/hannah-25/attune_be/actions/runs/30479898571), loadtest 프로파일 재전환은 [deploy run #30480622732](https://github.com/hannah-25/attune_be/actions/runs/30480622732)에서 성공했다.
- 결과 기록 원칙: k6 summary와 서버 지표만 남기며, 테스트 계정 비밀번호·JWT·외부 인증 토큰은 결과물에 기록하지 않는다.

| 항목 | 결과 |
| --- | --- |
| 총 실행 시간 | 4시간 45분 31초 (25 VU 워밍업 30분, 100 VU 유지 4시간, 종료 관찰 15분) |
| 완료 iteration | 388,408 |
| HTTP 요청 | 1,087,600 (평균 63.49 req/s) |
| HTTP 오류율 | 0% |
| HTTP 지연시간 | 평균 168.47 ms, 중앙값 164.23 ms, p90 171.71 ms, p95 174.16 ms |

#### 외부 호출 부하 사전 점검

- Gemini와 Google Calendar/OAuth 호출은 현재 요청 처리 스레드에서 동기적으로 수행된다. 외부 서비스가 느리면 해당 요청은 외부 응답을 기다리는 동안 서버 처리 여유를 점유할 수 있다.
- Gemini는 연결 5초·응답 30초 제한이며, 502/503/504 또는 연결 실패일 때 300 ms 뒤 1회 재시도한다. 외부 장애 시 한 요청이 약 60초까지 기다릴 수 있으므로, 혼합 시험에서는 Gemini 동시 호출 수를 낮게 제한한다.
- Google Calendar/OAuth는 연결 5초·응답 10초 제한이다. Calendar 연결·동기화도 별도 저부하 호출로 시작한다.
- 메일과 관리자 푸시는 비동기 executor에서 처리한다. Web Push는 연결·응답·커넥션 대기 5초 제한, route당 50개·전체 200개 연결 제한을 사용한다.
- 따라서 외부 연동 혼합 부하는 `100 VU 전체가 외부 호출`하는 방식으로 실행하지 않는다. 일반 조회·복약 부하를 유지하고, 소수의 외부 호출을 별도 시나리오로 동시 실행해 일반 API의 p95/p99·오류율·CPU가 악화되는지 확인한다.

### 4. 운영 준비 확인

1. dev 배포 후 readiness 통과와 정상 API 확인
2. 배포 전 CI, secret 존재 여부, migration 여부를 체크리스트로 확인
3. 롤백 절차를 dev에서 문서대로 1회 리허설하되, 운영에는 적용하지 않음
4. 오류가 발생한 시험에서는 `requestId` → 애플리케이션 로그 → Actuator → metric 순서로 원인 추적 가능함을 확인
5. 모든 테스트 계정·외부 연결·수신 구독·테스트 일정과 산출물에 토큰/개인정보가 남지 않았는지 확인

- [ ] 실제 클라이언트 핵심 E2E 흐름과 계정 삭제를 통과했다.
- [ ] 100 VU 4시간 장기 안정성 기준을 통과하거나, 실패 원인과 개선 조치를 확정했다.
- [ ] 배포·관측·롤백·정리 절차를 dev에서 검증했다.
- [ ] 모든 전용 데이터·외부 연결·테스트 구독을 삭제했고 dev를 일반 프로파일로 복구했다.

## 위험과 롤백

- 실제 메일·푸시·Gemini 호출은 비용과 외부 영향을 일으킬 수 있으므로 사전 승인 없이 실행하지 않는다. 현재 실제 사용자는 없으므로, 승인 뒤 전용 테스트 계정 묶음에는 모든 발송 기능을 실제 호출로 검증한다.
- OAuth/Calendar 권한은 테스트 계정에만 부여하고, 완료 후 공급자 콘솔과 앱에서 모두 연결을 해제한다.
- 외부 연동 또는 부하 시험 중 문제 발생 시 테스트를 중지하고 `loadtest=false`로 dev를 복구한다. 애플리케이션 코드 변경이 필요하면 별도 feature 브랜치와 PR로 수정한다.
